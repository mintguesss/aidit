# Aidit — 對話規則

系統有兩個對話介面，規則不同，不可混用。

- **A 課表微調** — 綁在課表上，工作是改條件重新求解
- **B 修業問答** — 通用入口，工作是把問題路由到既有能力

兩者都**不是聊天機器人**。共同底線：LLM 只負責理解問題與組織措辭，**一切判定由確定性引擎產出**。

---

## 零、共同規則（兩個介面都適用）

### 0.1 判定不得由 LLM 生成

任何關於學分、畢業資格、採計、擋修的結論，必須來自 `credit.audit` / `schedule.solve` / 規則包。LLM 不得自行推論這些內容，即使它「知道」答案。

實作上：LLM 的輸出經過 schema 驗證，只允許回傳**意圖與參數**，不允許回傳判定結果。

```ts
// 允許
{ intent: "adjust-plan", delta: { avoidDays: [5] } }

// 禁止
{ answer: "你還差 5 學分" }
```

### 0.2 三種回答，沒有第四種

| 類型 | 條件 | 形式 |
|---|---|---|
| **可判定** | 引擎有結果且依據通過驗證 | 給答案 + 依據 |
| **不確定** | 依據不足、規則有洞、資料缺漏 | 說明查過什麼、為何不能判定、建議洽詢誰 |
| **超出範圍** | 不屬於系統能力 | 明講做不到，指向承辦單位 |

**沒有「大概是」「應該可以」這種回答。**

### 0.3 無依據不作答

引用不到規章條文或引擎結果的內容，一律不說。不得以模型記憶中的「一般大學的規定」補足。

### 0.4 不執行寫入

不選課、不送申請、不改任何校務資料。使用者要求時明確說明系統無此能力，並告知正確管道。

### 0.5 外部內容不可信

檢索到的論壇、公告、網頁內容一律包成資料區塊，不進入指令通道。命中注入樣式即丟棄並記入 trace。

### 0.6 每輪寫 trace

意圖解析結果、呼叫了哪些工具、耗時、是否重試、是否轉人工。對話輪次也是 trace 的一部分。

### 0.7 上限

- 每輪 LLM 呼叫 ≤ 2 次
- 澄清提問每個問題 ≤ 1 次，再不明確就轉「超出範圍」
- 單一對話 session ≤ 20 輪，超過提示重新開始

## 一、A 介面：課表微調

### 1.1 對話狀態是約束集合，不是訊息歷史

每輪的產物是一個 `ConstraintDelta`，套用到目前的約束集合上，然後重跑求解器。

```ts
type ConstraintDelta = {
  avoidDays?: number[];
  avoidPeriods?: { day: number; periods: number[] }[];
  maxCredits?: number;
  minCredits?: number;
  excludeCourses?: string[];     // 課號
  pinCourses?: string[];         // 一定要留的課
  goals?: ("early-graduation" | "minor" | "cert-program")[];
  reason: string;                // 這次改了什麼、為什麼
};
```

**好處**：對話可以很長，但狀態永遠是一個小物件，不會因為歷史變長而漂移。使用者也能隨時看到目前的條件清單並直接編輯。

### 1.2 課表只能由求解器產出

LLM 不得列出課程、不得修改課號、不得調整學分。它只輸出 delta。

如果使用者說「幫我加一門機器學習」，流程是：查開課資料 → 找到課號 → 放進 `pinCourses` → 重跑求解 → 求解器決定其他課怎麼配合。不是 LLM 直接把那門課寫進課表。

### 1.3 每輪必須回報三件事

```
1. 改了什麼條件      「已排除週五所有時段」
2. 課表差異          「移除 IM4033，改為 IM4028（三 6-8）」
3. 代價              「通識自然科技領域只剩 1 門可選，餘額 3」
```

第 3 點最重要。只回新課表而不講代價，就跟一般的篩選器沒兩樣。

### 1.4 無解時不自動放寬

回報衝突原因，並**提出**放寬建議，由使用者決定。

```
找不到可行組合。
週五排除後，通識自然科技領域的 2 門課都在週五。
可以考慮：解除週五限制／改修暑期班／下學期再補。
```

不要自己偷偷放寬條件然後給一份看起來可行的課表。

### 1.5 允許的意圖清單

| 意圖 | 例句 |
|---|---|
| `adjust-time` | 把週五的課拿掉、不要早八 |
| `adjust-load` | 我想輕鬆一點、這學期多修一點 |
| `swap-course` | 這門換掉、我想修某某老師的課 |
| `pin-course` | 這門一定要留 |
| `change-goal` | 我想提前畢業、我要加修學程 |
| `explain` | 為什麼選這門、為什麼沒有某某課 |
| `compare` | 再給我一版、跟上一版差在哪 |

清單外的，一律走 §0.2 的「超出範圍」。

### 1.6 `explain` 要能回答「為什麼沒選某門課」

這是使用者最常問的，也是求解器可以直接回答的：該課在哪一步被排除（類別不符／擋修未過／衝堂／餘額 0）。**這條做好，整個系統的可信度會明顯不同。**

## 二、B 介面：修業問答

### 2.1 它是路由器，不是問答機

收到問題後先分類，再決定呼叫什麼。**不允許直接生成答案。**

```
問題 → 意圖分類 → 呼叫對應能力 → 用引擎結果組織回答
                 ↓ 分不出來
              超出範圍
```

### 2.2 意圖分類

| 意圖 | 處理方式 | 例句 |
|---|---|---|
| `personal-audit` | 呼叫審查引擎 | 我還差幾學分？通識夠了嗎？ |
| `regulation` | 查規則包／公告庫，**必附條文出處** | 超修可以流用嗎？輔系要幾學分？ |
| `course-info` | 查開課資料庫 | 資料探勘什麼時候開？誰教？ |
| `procedure` | 查流程資料，指向承辦單位 | 抵免要怎麼申請？ |
| `what-if` | 改條件重跑引擎 | 我提前畢業有可能嗎？ |
| `plan` | 導向 A 介面 | 幫我排下學期的課 |
| `out-of-scope` | 明講做不到 | 其餘一切 |

### 2.3 `regulation` 查無結果時的行為

**說找不到，不要用常識補。**

```
在 111 學年度課程規劃表與學則中查無關於此事的明文規定。
建議洽系辦公室課務承辦人確認。
```

這是最容易出事的地方。模型對「一般大學的規定」有很強的先驗，很容易編出一條聽起來很合理的規則。實作上要在 prompt 明確禁止，並用 schema 強制：沒有 citation 就不得回傳答案。

### 2.4 明確禁止的主題

| 禁止 | 理由 |
|---|---|
| 成績預測、被當機率 | 依據不足、偏誤風險 |
| 教師評價、給分甜不甜 | 個資與名譽、來源不可查證 |
| 代為申請、代為選課 | 系統無此能力，且辦法禁止 |
| 法律、醫療、心理諮商建議 | 超出場域 |
| 非本校事務 | 超出場域 |
| 其他學生的資料 | 權限 |

碰到這些一律簡短回絕並指向正確管道，不要解釋一長串。

### 2.5 能力邊界要主動說

系統只支援資管系 111 學年度。其他系所或學年度的問題，直接說明尚未支援，不要硬答。

Provider 的 `capabilities()` 缺哪一項（例如沒有抵免資料），相關問題也要說明資料不足。

## 三、回答格式模板

### 可判定

```
[結論一句話]
[依據：文件、頁次]
[必要時：本結果未計入 N 項待確認事項]
```

### 不確定

```
無法判定。
已查詢：[查過哪些來源]
原因：[為何不足]
建議洽詢：[單位]
```

### 超出範圍

```
這不在系統能力範圍內。
[一句話指向正確管道]
```

三種都**短**。長篇大論會讓人以為系統在掩飾不確定。

---

## 四、給競賽的說法

辦法排除的是「**僅**具單輪問答、純文件檢索問答」的作品 —— 關鍵在「僅」。有問答功能不會不合格。

但要在簡報裡把定位講清楚：

> 對話不是我們的主要介面，而是引擎的第二入口。
> 使用者打開系統看到的是審查報表，不是對話框。
> 對話的工作是改變條件重新求解，不是生成答案 ——
> 所有判定都來自確定性引擎，對話層只負責理解與措辭。

配合 trace 上看得到「每一輪對話呼叫了哪些工具」，這個主張就站得住。

**反面教材**：如果 demo 影片一開場就是對話框，再怎麼解釋都會被歸類成聊天機器人。影片的第一個畫面應該是審查結果頁。
