# SPEC-CHANGES —— 規格異動與實作偏差紀錄

本檔記錄實作過程中，對 `SPEC.md`、`BACKEND.md` 與 `CONVERSATION.md` 的**所有**偏差、
擴充與待決事項。三份規格書維持原樣不動；凡與其不一致之處，一律在此留下條目與理由。
（`CONVERSATION.md` 於開發中補上，自 §E11 起納入本檔的記錄範圍。）

規則：

1. 每一條都要寫清楚：**改了什麼、為什麼、影響到哪裡、怎麼還原**。
2. 只要動到規格書描述的行為，就必須在此新增條目，不得只改程式。
3. 條目一旦寫入不刪除；後續若推翻，追加一條「取代 #N」而不是改掉舊條目。
4. 待決事項集中在 §D，等使用者決定後再轉為正式條目。

版本：對應 2026-09-14 之實作狀態。

## A. 必要偏差（不改就跑不起來，或會出錯）

### A1　`temperature: 0` 在現行 Claude 模型已移除

- **規格**：BACKEND.md §7 要求執行期 LLM 呼叫使用 `temperature: 0`。
- **實作**：未送出 `temperature`。
- **理由**：Claude Opus 5、Sonnet 5 等現行模型已移除取樣參數，送出 `temperature` 會得到
  HTTP 400。這不是選擇，是 API 契約變更。
- **替代做法**：以三道機制取代「靠 temperature 求確定性」：
  1. structured output（`output_config.format` + zod schema），輸出形狀被強制約束；
  2. schema 驗證失敗即重試一次，仍失敗則降級為 HoldItem 或請使用者澄清；
  3. `output_config.effort: "low"` 控制推理深度，壓低發散空間。
- **影響**：LLM 輸出不再具備「同輸入必同輸出」的保證。但本系統的設計本來就不依賴這點 ——
  學分計算、求解、引用查核全部是確定性程式，LLM 只產生「會被 schema 與原文回查雙重驗證的結構化資料」。
- **位置**：`src/lib/llm/client.ts`
- **還原方式**：若日後模型恢復支援取樣參數，於 `structured()` 加回即可，不影響其他模組。

### A2　`response_format` 改為 `output_config.format`

- **規格**：BACKEND.md §7 寫 `response_format: structured`。
- **實作**：`client.messages.parse({ output_config: { format: zodOutputFormat(schema) } })`。
- **理由**：Anthropic SDK 的參數名稱與呼叫方式已改版；`output_format` 為已棄用參數。
- **位置**：`src/lib/llm/client.ts`

### A3　規則抽取的 PDF 解析拆成獨立的 Python 步驟

- **規格**：BACKEND.md §2 的流程圖把 pdfplumber 畫在同一條管線內。
- **實作**：拆成兩支程式：
  - `scripts/pdf-to-segments.py`（Python + pdfplumber，輸出分段文字 JSON）
  - `scripts/extract-rulepack.ts`（Node，讀 JSON → LLM 抽取 → 草稿 + 語料檔）
- **理由**：SPEC.md §1 明定「避免引入 Python 依賴」，但 pdfplumber 本身就是 Python。
  拆開後 Node 端沒有 Python 依賴，PDF 解析是一次性的離線前處理，可在任何有 Python 的機器上跑。
- **影響**：匯入真實 PDF 時多一個指令；換來的是主程式零 Python 依賴。

## B. 設計擴充（規格未涵蓋，但不做會有洞）

### B1　`ambiguity.affects` 欄位

- **規格**：SPEC.md §5 的 `ambiguities` 沒有描述「影響範圍」。
- **擴充**：新增 `affects: "thisCategory" | "undetermined"`。
- **理由**：兩種待確認事項的性質不同：
  - 跨院選修 → 解消後確定落在系專業選修（`thisCategory`），可算出「採計後未修 3 → 0」；
  - 抵免課號查無對照 → 連歸屬類別本身都不知道（`undetermined`），無法算出影響數字。
    沒有這個欄位，第二種只能硬掰一個類別，HoldItem 的 `impact` 就會寫出假的數字。
- **位置**：`src/lib/rules/schema.ts`、`src/lib/audit/engine.ts`

### B2　`RulePack.provenance` 與 `approvedBy`

- **擴充**：新增 `provenance: "approved" | "draft" | "synthetic"`、`approvedBy`、`contentHash`。
- **理由**：BACKEND.md §2 要求「鎖定版本 + content hash」與人工校對紀錄，但 §5 的規則包
  schema 沒有對應欄位。沒有 provenance 就無法在執行期擋下「未校對的草稿」。
- **行為**：`provenance === "draft"` 的規則包，`resolveRulePack()` 直接拒絕，整案中止。
  `synthetic` 可用於 Demo 與評測，但 UI 會在學籍卡明白標示「不得作為實際審查依據」。
- **位置**：`src/lib/rules/schema.ts`、`src/lib/rules/loader.ts`、`src/components/Rail.tsx`

### B3　`CategoryResult` 新增 `shortName` 與 `assignedCodes`

- **理由**：`shortName` 供修業尺使用（類別全名會把橫條擠爆）；`assignedCodes` 讓「這門課被採計為
  系專業選修」這條結論可以在 UI 上被逐條查核，否則指派結果是黑箱。

### B4　`StudentRecord.plannedCommitments`

- **理由**：Demo 的「與校外實習登記時段（五 2-4）重疊」需要一個資料來源。
  沒有這欄，求解器就無從說明「哪兩個條件在打架」——而那是 SPEC.md §12 指定的賣點。

### B5　`GraduationEvidence.label`

- **理由**：畢業條件的顯示字樣不只有「通過／未通過」（服務學習顯示「已完成」、中文能力顯示「免測」）。
  把顯示字樣寫死在引擎裡會讓每加一個條件就要改程式。

### B6　`Plan.warnings` 與 `Plan.appliedConstraints`

- **理由**：SPEC.md §5 只要求把「放寬了什麼」寫出來。實作發現還有兩類同樣重要的資訊：
  - `warnings`：做不到的偏好、低於學期學分下限、含時段未知的課程；
  - `appliedConstraints`：這份課表究竟是照哪些條件排出來的。
    兩者都是「使用者要能檢查系統」的必要資訊。

### B7　`overflowInProgress` 的處理

- **規格**：SPEC.md §3 只定義 `overflow`（超修）。
- **實作**：修課中學分若超出該類別應修學分，另計為 `overflowInProgress`，寫進類別 `notes`，
  但**不**計入 `overflow`。
- **理由**：不變式 `totalEarned === countable + overflow` 要求 `overflow` 只能是「已修得」的超出部分。
  把修課中的超出部分混進去會讓不變式失效。

## C. 行為差異（與規格字面不同，但更符合規格的意圖）

### C1　`fewest-courses` 不得交出補不完未修學分的方案

- **規格**：BACKEND.md §5 的 `OBJECTIVES` 寫 `"fewest-courses": s => [s.courseCount, s.unmetAfter]`。
- **問題**：照字面實作，「一門課都不選」的 courseCount = 0 最小，會勝過任何補足未修的方案。
  實測時確實跑出「1 門課、仍差 3 學分」的建議。
- **實作**：先把候選解限縮到「能達到的最小未修學分」那一群，再套 preset 的目標函數。
- **理由**：在畢業審查場域，「比較少堂數但畢不了業」不是一個選項，是一份錯的建議。

### C2　求解器的「無解」包含「補不完」

- **規格**：BACKEND.md §5 的 infeasible 定義為「任一 unmet 類別的候選集為空」。
- **實作**：候選集非空但最佳解仍有未修學分時，也先走放寬流程；全部放寬過仍補不完，
  才回傳最佳的部分方案，並在 `warnings` 標明「執行後仍有未修學分」。
- **理由**：條件太緊（如學分上限 2）時，候選集不空但湊不出完整方案。
  直接交出一份補不完的課表，比誠實說「這些條件湊不出解」更容易誤導人。

### C3　放寬順序的第三順位改為「避開早八」

- **規格**：BACKEND.md §5 的放寬順序是 `maxCredits → avoidDays → 允許 extracted 先修未過`。
- **實作**：`maxCredits → avoidDays → avoidEarly`。
- **理由**：第三項在本實作中是 no-op —— `extracted` 信心的先修**本來就不是硬限制**
  （BACKEND.md §4 明定「不要讓低信心的抽取結果去排除課程」），所以沒有東西可以放寬。
  改為放寬「避開早八」這個真正會造成無解的軟條件。

### C4　`fill-unmet` 的第二順位加入「達學期學分下限」

- **理由**：低於學則下限的學期不是合法的修課量。補足未修卻交出一份不能送出的課表沒有意義。
- **限制**：僅作為排序偏好，不是硬限制（畢業當學期常可專案申請）；
  低於下限時一律在 `warnings` 標明，由學生自行確認。

### C5　同一 ambiguity 的多門課合併為一則 HoldItem

- **規格**：SPEC.md §5 說「命中 trigger 時產生一個 HoldItem」，讀起來像逐課一則。
- **實作**：同一條 ambiguity 命中多門課時，合併為一則，列出所有涉及科目。
- **理由**：規則的洞只有一個，洽詢對象與依據也只有一份。逐課一則會讓待確認分頁被洗版，
  而且學生拿著三張內容幾乎相同的洽詢單去系辦並沒有比較好。

### C6　`safety.scan` 一則內容只產生一筆攔截紀錄

- **實作**：一則外部內容即使命中多個樣式，也只記一筆，`patternMatched` 列出所有命中樣式。
- **理由**：逐樣式各記一筆會讓 trace 上的「攔截則數」變成「命中樣式數」，
  評測報告的攔截率會對不上實際的內容筆數。

### C7　`capabilities()` 描述來源能力，不是資料內容

- **實作**：`MockProvider.capabilities().hasWaivers` 恆為 `true`。
- **理由**：最初誤把「這份資料沒有抵免」當成「這個來源不提供抵免」，導致沒有抵免的學生
  憑空多出一筆「資料來源未含抵免紀錄」的待確認事項（評測時 7 個案例因此不符）。
  `UploadProvider` 則維持依內容判定 —— 匯出檔沒有抵免欄位時，系統確實無法分辨兩者，
  轉人工是正確行為。

### C8　模糊比對的滑動視窗步長改為 1

- **規格**：BACKEND.md §3 的 `fuzzyBestMatch` 未規定步長。
- **實作**：needle ≤ 200 字時逐字滑動。
- **理由**：原本用 `n/4` 當步長，會錯過最佳對齊位置，讓只差一個字的引用被判成「原文查無」，
  進而把一條正確的結論誤降為待確認。引用片段一般 < 60 字，逐字滑動的成本可忽略。

## E. 使用者於開發中提出的變更

### E1　選課建議改為「先依選課傾向產生，再以對話微調」

- **提出時間**：2026-09-14，開發中。
- **原規格**：SPEC.md §8 的 `/api/plan` 以 `preset: "fill-unmet" | "no-early" | "fewest-courses"`
  三選一，UI 上是三顆方案按鈕（見 `aidit-demo-v5.html`）。
- **變更後**：
  1. 學生在**基本資料**填寫選課傾向（修課目標、是否排早八、要空出的星期、期望堂數、
     學分上限、是否希望課程集中）；
  2. 第一版課表直接依此傾向求解，不再是三個罐頭方案；
  3. 之後以自然語言微調（「不要早八」「少一堂課」「空出星期五」「課盡量集中」「重來」），
     每次微調都重跑確定性求解器。
- **理由（使用者原話）**：先根據讓學生在基本資料填寫的選課傾向、目標等等來制定，
  後續再根據對話式來微調。
- **實作**：
  - 新增 `CoursePreferences`、`PlanAdjustment`、`AdjustmentOutcome` 型別（`src/lib/types.ts`）
  - `StudentRecord.preferences` 承載基本資料填寫的傾向
  - `SolveContext.preferences` + `objectiveFor()`：目標函數由傾向組出，不再是 `OBJECTIVES` 查表
  - `constraintsFrom()` / `describeConstraints()`：傾向 → 求解條件 → 人看得懂的句子
  - `src/lib/planning/adjust.ts`：一句話 → 結構化調整 → 套用到傾向
  - `POST /api/plan` 改為接受 `{ preferences, adjustment }`，回傳生效條件與做不到的偏好
  - UI：`PlanPanel`（條件列 + 課表 + 微調輸入 + 調整紀錄）、左欄新增「選課傾向」卡
- **硬／軟限制的界線**（這是本次變更最需要說明的設計決定）：
  - **硬限制**：`avoidDays`（空出的星期）—— 那幾天完全不排課；
  - **軟偏好**：`avoidEarly`、`targetCourseCount`、`preferCompactDays` —— 只影響排序。
    把「不要早八」做成硬限制，會讓「唯一開課就是早八」的情況變成無解；
    正確的回答是照排、並在 `warnings` 說明「你設定了不排早八，但這個類別只有早八可選」。
- **preset 的去留**：`Preset` 型別與 `/api/plan` 的契約保留，由 `PRESET_OF_GOAL` 從目標推導，
  維持 SPEC.md §8 的 API 形狀不變。

### E2　新增第三處執行期 LLM 用途

- **原規格**：BACKEND.md §7 明列「只有三處允許呼叫 LLM」：規則抽取（離線）、
  `rule.reconcile`、情境試算意圖解析。
- **變更**：新增第四處 —— 選課建議的對話式微調意圖解析（`parseAdjustment`）。
- **理由**：E1 的對話式微調需要把「少一堂課」對應到結構化調整。
- **為什麼這不算破壞 §7 的意圖**：§7 真正的主張是
  「`credit.audit` / `schedule.solve` / `citation.verify` 是確定性運算，不得有模型」。
  本次新增的用途與「情境試算意圖解析」完全同型：
  - 模型只輸出 `PlanAdjustment[]`，經 zod schema 驗證；
  - 不輸出課號、課名、學分或任何判定；

### E10　新增總體對話助理（第四處執行期 LLM 用途）

- **提出時間**：2026-09-14，開發中。
- **理由（使用者原話）**：除了課表那邊還要有一個總體性的對話框，啥都能回答。
- **與系統核心主張的張力，以及處理方式**：
  「啥都能回答」與「零錯答」會打架。本實作的解法是把**能聊的範圍**與**能斷言的內容**分開：
  1. 助理可以聊的話題不設限 —— 審查結果解讀、規定的意思、選課策略、系統怎麼運作；
  2. 但它能講的每一個學分數字，都只能引用 `buildGrounding()` 產生的**事實底稿**，
     而底稿裡的每一個數字都來自確定性引擎。System prompt 明文禁止模型自行加總或估計；
  3. 需要「改變條件後重新推算」的題目（提前畢業、停修、加修輔系或學程、調整課表），
     模型只負責辨識意圖，實際推算由 `simulate()` 與 `solveWithRelaxation()` 執行，
     結果由路由算完後附回，模型的回覆只寫一句引導語；
  4. 成績預測、被當機率、教師評價、錄取機會一律拒答，且回傳拒答分類。
- **偏差**：BACKEND.md §7 明列「只有三處允許呼叫 LLM」。本次新增第四處。
  §7 真正的主張是「`credit.audit` / `schedule.solve` / `citation.verify` 不得有模型」，
  這條完全沒有鬆動：`tests/boundaries.test.ts` 的受保護模組清單不變，CI 第 4 項照常通過。
- **離線替身**：以關鍵詞比對 + 事實模板回答，涵蓋還差多少學分、超修為何不能算、
  待確認事項、規劃表版本、各類別狀況、下學期建議、成績平均、系統原理等常見問題；
  對不上就明說離線模式的限制，不用相似度硬湊。
- **驗證**：`tests/chat.test.ts` 14 項，重點不在「回答得好不好」，而在
  （a）助理講的數字等於引擎算的數字、（b）該拒答的確實拒答、
  （c）需要推算的題目確實交給確定性程式且回覆不自行下結論。
- **位置**：`src/lib/chat/`、`src/app/api/chat/route.ts`、`src/app/assistant/page.tsx`

### E12　學期學分下限視為硬規定，不是偏好

- **提出時間**：2026-09-14，開發中。
- **理由（使用者原話）**：怎麼會有沒辦法滿足的條件 既然下限九學分就應該照規定至少9 怎麼會只給他6。
- **原本的行為（錯的）**：求解器把 `termMinCredits` 當成評分項，
  當「補足未修學分」只需要 6 學分時就交出 6 學分的方案，再以 warning 說「低於下限 9」。
  這把**學則的硬規定**降級成了系統的偏好，等於建議學生違規。
- **改法**：
  1. 候選集合新增 `fillers` —— 不對應任何未修學分、但學生法定可修的課程。
     原本的候選只含「能補未修學分的課」，所以湊不滿 9 學分時無課可加。
  2. 在同樣達成最小 `unmetAfter` 的解之中，**只要存在**達到 `termMinCredits` 的解，
     就一律只保留那些解；達不到時才退回原本的評分邏輯並照實說明原因。
- **與 §C4 的關係**：§C4 只是把「達下限」放進 `fill-unmet` 的評分順位，力道不足。本條取代之。
- **影響**：demo 案例的第一版課表由 6 學分／2 門 變成 9 學分／3 門。
- **位置**：`src/lib/solver/schedule.ts` 的 `filterCandidates()` 與 `solveInner()`

  （SPEC.md §6 step 2：兩個入學學年不一致即轉人工）。系統只講清楚

- **情境目錄**：七個情境分成四組 —— 畢業時程／加修另一套規定／改變學籍／門檻查詢，

### E58　偏好的隱私分層與使用者控制

- **提出時間**：2026-09-17，使用者指定的規則。
- **規格關係**：SPEC.md §9 只規定「修課紀錄不落地」與「trace 去識別」，
  對**使用者自填的偏好**沒有任何規定。本條補上分層、控制與自動過期。
- **欄位分層**：
  - **必填**（規劃所需，正常儲存）：修課目標、避開時段、期望堂數、學期學分上限、
    課程集中度、備註、額外修業目標。已排定時段來自校務系統，不由使用者填。
  - **選填**（僅影響排序）：職涯方向、興趣領域、想避開的課程類型。
- **「僅影響排序」是實作保證，不是文案**：選填偏好算出的 `affinity` 排在
  **所有規劃條件之後、確定性 tie-break 之前** ——
  只有當兩份課表在未修學分、堂數、早八、集中度、學期下限上完全相同時，
  它才會決定誰排前面。比對方式是單純的關鍵詞出現與否（課名、通識領域），
  不是語意比對，也沒有 LLM：選填欄位是自由文字，用相似度去猜會讓排序變得無法解釋。
  `tests/extra-goals.test.ts` 驗證填與不填得到相同的可行性、學分、未修學分與課程集合。
- **資料模型分開存放**：`{ required, optional, lastUsedAt }`。分開存不只是為了畫面好標示 ——
  「只刪選填」要能成為一個乾淨的動作，就不能逐欄去挑。舊版的扁平格式會自動遷移為 `required`。
- **新增 `/privacy`「資料與隱私」頁**：
  1. **查閱** —— 逐欄列出目前存了什麼值，必填／選填分區，並說明各自的性質。
  2. **只刪選填** —— 必填保留，系統仍可正常使用。
  3. **全部刪除**。
  4. **匯出 JSON**。
  刪除立即生效、不做二次確認：被誤刪的代價只是重填一次偏好，
  而多一道確認只會讓真的想刪的人更難刪。
- **自動過期**：
  - 最後使用日起 12 個月未使用 → 讀取時即刪除（`loadStored` 內判定）。
  - 學籍狀態變更為畢業或離校 → `PrefLifecycle` 在**每一頁**檢查並刪除。
    只在個人資料頁檢查的話，畢業生只要不點進那一頁就永遠不會被清掉。
- **trace 保留 90 天**：`TRACE_TTL_DAYS` 與 `purgeExpired()` 原本就寫好了，
  但**從來沒有人呼叫它** —— 保留政策等於只是一句寫在型別旁邊的註解。
  新增 `purgeDaily()`（每次請求檢查、24 小時內只跑一次）掛在 `getAuditSession`，
  並提供 `scripts/purge.ts` 供 Windows 工作排程器每日觸發。
  日誌只記筆數與時間，不含任何個人識別資訊 —— 這份日誌本身也不該變成個資來源。
- **措辭的精確性（後續修正）**：初版寫「伺服器沒有副本」，那講的是**不落地**，
  但偏好**每次請求都會送到伺服器**（求解器需要它才排得出課表）。兩者差很多，
  隱私頁上不能含糊，已改為「排課時隨請求送出，伺服器算完即丟」。
  同時補上一列說明**送進語言模型的只有使用者打的那句話** ——
  偏好、學號、成績從未進入任何 prompt（`parsePlanIntent` / `parseAskIntent` 的
  user 訊息只有 `renderHistory(messages)`；情境試算另加學期代號與未修課程名稱）。
  這是 CONVERSATION.md §0.1「LLM 只輸出意圖與參數」的副產品：
  模型要的是意圖，求解器要的是條件，兩者本來就分開。
- **入口**：頁尾加連結，並收進「更多」選單；不佔主導覽。
- **位置**：`src/lib/ui/prefs.ts`、`src/lib/solver/schedule.ts`、`src/app/privacy/page.tsx`、

### E60　偏好改存伺服器端，「刪除」才成為一項權利（修正 §E58）

- **提出時間**：2026-09-17，使用者指出。
- **理由（使用者原話）**：我覺得全部都可以存在線上阿 不然都在本地的話要刪除功能幹嘛。
- **這個質疑是對的**：查閱／刪除／匯出是**資料主體權利**的形狀，而那些權利之所以存在，
  正是因為資料在別人手上。蓋在 localStorage 上，使用者本來就能從瀏覽器設定清掉 ——
  那個按鈕只是比較好按而已，不是一項權利。
  而且 §E58 還留下一個更矛盾的地方：伺服器**確實**持有執行紀錄，

  真正該能刪的刪不掉，刪得掉的本來就在使用者手上。
- **改法**：
  1. 新增 `src/lib/store/prefs-store.ts`：以 `studentHash`（HMAC，不可逆）為鍵存放偏好，
     必填與選填仍分開。伺服器上不存任何可識別欄位。
  2. 新增 `POST/DELETE /api/preferences`：讀取、寫入、只刪選填、刪全部偏好、
     連同執行紀錄一起刪。刪除是真的移除檔案，不是標記為已刪除。
  3. `TraceStore` 新增 `purgeByStudent(studentHash)`（檔案與 Supabase 兩種實作都有）。
  4. 前端改為**伺服器是權威來源**，localStorage 退為離線備援與快取
     （`src/lib/ui/sync.ts`）。連不上伺服器時回退本機值，不中斷流程。
  5. 每日清理一併涵蓋偏好（12 個月未使用、畢業或離校）。
- **執行紀錄的刪除獨立成一個動作**，因為它的代價完全不同：那是系統對自己判定的稽核證據，
  刪掉之後「當初告訴我什麼、依據哪一條」就再也查不到 —— 包括使用者自己想回頭確認的時候。
  畫面上把這句話寫出來，不讓它看起來像一個無害的清理動作。
- **換來的義務**：這份資料從此需要被管理（保留期限、自動刪除、刪除權）。
  這正是把它放在伺服器的代價，也是那四項控制之所以有意義的原因。
- **驗證**：`tests/extra-goals.test.ts` 新增 6 項 —— 存取往返、只刪選填後必填仍在、
  全部刪除是真的刪掉、畢業離校時讀取即刪除、12 個月過期判定、

- **更根本的問題**：`Student` 早就有 `minors` / `doubleMajors` / `certPrograms` 三個欄位，
  那是校務系統的**註冊事實**。系統本來就知道，不該等學生自己再宣告一次。
- **改法**：
  1. 共用 `PREFERENCES.extraGoals` 改為空陣列。
  2. 新增 `registeredGoals(student)`：由學籍資料推導已註冊的輔系／雙主修／學程。
     `/api/extra-goals` 一律取用，並與學生自行宣告的合併（重複的不列兩次，已註冊優先）。
     **一般生沒有那三個欄位，整個區塊自然不出現。**
  3. `ExtraGoalSummary` 新增 `registered`，UI 對自行宣告的標示「自行宣告，尚未註冊」——
     「已經註冊」與「打算要修」是兩件事，畫面上要分得出來。
  4. 個人資料頁的說明改為：已註冊的會自動顯示，這裡填的是還沒註冊但打算修的。
  5. `minor-student` 案例改為「輔系與學分學程學生」（`minors` ＋ `certPrograms`），
     不再靠 preference 硬塞；`double-major` 案例本來就有 `doubleMajors`，自動生效。
- **驗證**：新增 3 項 —— 一般生（`plain`）沒有任何額外目標、
  有註冊的案例由學籍資料推導、已註冊與自行宣告分得開且重複的不列兩次。
- **截圖一併修正**：`01-home` 的說明拿掉「額外修業目標」（demo 已經沒有），
  另以 `minor-student` 補拍兩張（`18-extra-goals-home`、`19-extra-goals-audit`）。
  截圖索引加註為什麼那兩張用不同案例。
- **位置**：`src/lib/providers/fixtures.ts`、`src/lib/extra/goals.ts`、
  `src/app/api/extra-goals/route.ts`、`src/components/audit/ExtraGoals.tsx`、
